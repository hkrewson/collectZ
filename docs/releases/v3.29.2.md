## Summary

Makes scheduled BookOrbit target advancement and durable job creation one atomic workspace-authorized operation.

## What changed

- Scheduled provider enqueue now locks and rechecks the due target inside the owning transaction.
- The same transaction creates or reuses the durable job and advances the target's `last_enqueued_at` timestamp.
- Workspace, library, provider connection, provider type, and actor ownership are derived from the locked target and authorized scheduler context rather than copied from the caller.
- A concurrent or repeated sweep sees the target as no longer due after the first committed enqueue and cannot create a second job for the cadence window.
- The BookOrbit authoritative import smoke proves failed-enqueue rollback, same-transaction writes, concurrent-sweep exclusion, successful worker processing, cadence reuse, and secret-free payloads.

## Breaking changes

None. Manual BookOrbit imports, provider connection configuration, scheduler readback, durable-job response shapes, and existing API routes are unchanged.

## Environment/config changes

None.

## Migration and data impact

No database migration or retained-data transformation is introduced. The existing `sync_jobs` row is the durable transactional queue record, and the current schema remains migration `144`.

## Security vulnerability triage

- High findings: backend and frontend production dependency audits must report zero blocking vulnerabilities.
- Authorization impact: the atomic operation continues through the existing actor-authorized workspace transaction and derives job ownership from the locked target.
- Evidence hygiene: job target payloads remain sanitized and the BookOrbit smoke verifies provider credentials do not appear in persisted target data or output.
- Owner: CollectZ maintainers.
- Target remediation milestone: `3.29.2` before release publication.

## Rollback guidance

Deploy the matching `3.29.1` backend and frontend together. No schema reversal is required because migration `144` remains current. A rollback restores the former two-transaction scheduled enqueue sequence but does not alter already-created durable jobs.

## Known issues and follow-up

The local observability evidence artifact still identifies `3.28.2`; its generator creates and resets separate logging stacks and volumes and therefore requires an explicit repository-policy exception. It is not a tagged-CI gate. Other mutation-plus-enqueue workflows remain backlog work and should adopt this pattern only when their owning transaction can create the durable job directly.
