# collectZ v3.24.14

## Version and date

- Version: `3.24.14`
- Date: `2026-10-10`

## Milestone target and status

- Roadmap slice: `3.24.14 - Non-Owner Runtime Database Role and Credential Split`
- Status: `complete locally against PostgreSQL 16; canonical Docker stack and hosted release gates pending`

## Summary

The backend no longer runs as the PostgreSQL owner/superuser. A one-shot `migrate` service applies migrations and provisions a least-privilege `collectz_app` role with the owner credential, then exits. The backend connects only as that role, and it refuses to start if its database credential is a superuser, owns application tables, or could bypass future row-level security.

## What changed

- Added a one-shot `migrate` Compose service built from the backend image. It runs `scripts/migrate-and-provision.js`, which applies pending migrations, creates or updates the runtime role, then connects as that role to verify it before exiting. The backend waits for it to complete successfully.
- The runtime role is created with `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, and `NOBYPASSRLS`. It gets `SELECT/INSERT/UPDATE/DELETE` on application tables and `USAGE/SELECT/UPDATE` on sequences. It cannot create schemas or objects, cannot truncate, index, or disable triggers, and has read-only access to `schema_migrations`. Owner default privileges give tables from future migrations the same grants.
- The role password is sent to PostgreSQL as a SCRAM-SHA-256 verifier computed by the job, so the plaintext never appears in SQL text or server statement logs. Each run removes any stray role membership that would let the runtime role inherit owner rights.
- Added a backend startup privilege guard (`DATABASE_RUNTIME_ROLE_POLICY`, `enforce` in Compose). It fails closed on superuser, `CREATEROLE`, `CREATEDB`, `REPLICATION`, or `BYPASSRLS`; on owned or inherited table ownership; on privileged role membership; and on schema or database `CREATE`.
- With `DATABASE_MIGRATIONS_MODE=external` (Compose), the backend checks that the schema is current and will not start against an un-migrated database. The legacy in-process runner remains available as `startup` mode for ad-hoc runs and logs a warning.
- Added the `runtime-role-certification` CI step and evidence artifact, a local preflight gate for that evidence, and unit coverage for the role, verifier, guard, and Compose contract.

## Breaking changes

- **New required setting:** `DB_RUNTIME_PASSWORD` must be set before `docker compose up`. Compose stops with an explicit error if it is missing. Use 16 or more characters from letters, digits, and `. _ ~ -` (for example `openssl rand -hex 24`). `./setup.sh --generate-secrets` fills it in for existing `.env` files.
- Deployments that run the backend image without the bundled Compose file must run `node scripts/migrate-and-provision.js` with the owner credential before starting the backend, then point the backend's `DATABASE_URL` at the runtime role. Otherwise, set `DATABASE_MIGRATIONS_MODE=startup` and accept the warning.

## Environment/config changes

- New: `DB_RUNTIME_PASSWORD` (required), `DB_RUNTIME_USER` (default `collectz_app`), `DATABASE_MIGRATIONS_MODE`, `DATABASE_RUNTIME_ROLE_POLICY`, and `DATABASE_MIGRATION_URL` (set by Compose for the `migrate` service only).
- `DB_PASSWORD` is now passed only to the `db` and `migrate` services; the backend container no longer receives it.

## Migration and data impact

- No schema migration is added; the chain stays at `122`.
- Existing databases upgrade in place: on its first run the `migrate` service creates the runtime role and grants it access to the existing tables. Data is not modified.
- Rotating `DB_RUNTIME_PASSWORD` requires only editing `.env` and running `docker compose up -d`.

## Deployment and verification

- Version metadata is synchronized at `3.24.14` and Help > Releases is regenerated from this note.
- Against a live PostgreSQL 16 server: the migrate job provisioned the role on a fresh database and re-ran idempotently; runtime-role certification passed `30/30` raw-SQL and guard checks, including a legacy `121 -> 122` upgrade; and the server statement log contained no plaintext runtime password.
- The backend started as the runtime role in both editions, and the API integration, RBAC, cross-type isolation, workspace authorization, sensitive-operation, auth-token abuse, workspace ownership, and sensitive-operation certification checks passed with no permission errors. Startup was refused for the owner credential under `enforce` and for an un-migrated schema under external migrations.
- Backend unit tests (`362`), OpenAPI, init parity, generic migration rehearsal, and identity-upgrade certification (`not_required`, baseline `122`) passed.

## Security vulnerability triage

- No dependency changes in this release; dependency audit results are unchanged from `3.24.13`.
- Hardening: if application code is ever compromised, the database credential it holds can no longer alter, drop, or truncate the schema, or bypass the row-level security that later slices will enable.

## Hosted release gates

- After push, require hosted `migration-check` (including the new runtime-role certification artifact), `compose-smoke`, `rbac-regression`, `browser-regression`, Core/control-plane `runtime-smoke`, `dependency-scan`, `secret-scan`, and `image-security-and-sbom` before promotion.

## Rollback guidance

- Roll back backend and frontend together to `3.24.13` with the `3.24.13` Compose file; it reconnects with the owner credential. The `collectz_app` role and its grants can stay in place, or you can remove them with `DROP OWNED BY collectz_app; DROP ROLE collectz_app;` as the owner.
- No schema rollback is required.

## Known issues and follow-up

- Row-level security policies, transaction-local workspace scope, and scope binding for jobs and maintenance commands remain in the backlog as the next slices of `Non-Owner Runtime Database Role and Staged Row-Level Security`.
- `init.sql` remains a parity-checked reference schema; retiring it stays with `Migration-Chain Fresh Installation Authority`.
