# collectZ v3.29.0

## Version and date

- Version: `3.29.0`
- Date: `2026-11-21`

## Milestone target and status

- Roadmap slice: `3.29.0 — Migration-Chain Fresh Installation Authority`.
- Status: release candidate. Version metadata, release artifacts, the canonical runtime, and Help > Releases are aligned locally; publication remains blocked on refreshed observability evidence and hosted certification of the version-closeout commit.

## Summary

Makes the append-only migration chain the sole authoritative path for fresh installation, retained upgrade, restored runtime, Core startup, and Platform startup, then retires the hand-maintained duplicate schema.

## What changed

- Expanded fresh-install certification across relations, columns, indexes, constraints, triggers, functions, row-level security objects, migration rows, feature flags, and required bootstrap rows.
- Certified exact non-owner runtime and broker role attributes, memberships, database/schema/table/sequence/function grants, default privileges, and broker mappings through a redacted provisioning inventory.
- Added hosted Core evidence proving the database was empty before migration startup and that the production backend runs through a non-owner credential in external migration mode after every migration is applied.
- Added restored-runtime authority evidence for database-native snapshots of migration-built databases, including exact retained counts, complete migration history, required bootstrap state, and non-owner runtime behavior.
- Added contained Platform certification that starts a production-mode control-plane backend from an empty migration-built scratch database inside the canonical stack and passes the complete edition boundary.
- Retired `init.sql` after the migration-built Core, Platform, retained-upgrade, restore, bootstrap, and ownership contracts were certified. The compatibility-named parity artifact now fails if that duplicate schema source reappears.
- Moved workspace-ownership table discovery from duplicate-schema parsing to a direct comparison between reviewed classifications and the live migration-built PostgreSQL catalog.

## Breaking changes

Fresh installations must use the one-shot migration/provisioning service. Directly applying the former root `init.sql` file is no longer supported. Existing installations continue upgrading through the same append-only migration chain, and no deployed migration was rewritten.

## Environment/config changes

No new operator environment variables are required. The split owner credential for the one-shot migration service and non-owner runtime credential remain mandatory. CI uses `MIGRATION_AUTHORITY_ADMIN_URL` and `MIGRATION_AUTHORITY_OUTPUT` for the renamed fresh-install authority gate; the previous `test:init-parity` command remains as a compatibility alias.

## Migration and data impact

No new schema migration is introduced by the version closeout. Migration `144` remains current. Certification repeatedly created and removed isolated scratch databases and ephemeral runtime/broker roles inside the existing PostgreSQL service without changing retained application rows. Operators upgrading from `3.28.2` run the normal migration service, which finds the schema current and reprovisions the reviewed runtime grants idempotently.

## Rollback guidance

Deploy the matching `3.28.2` backend and frontend together. The database schema remains at migration `144`, so application rollback does not require schema reversal. Do not restore the retired `init.sql` file as an installation path; retained installations and rollback validation continue using the append-only migration chain and reviewed database backup/restore procedure.

## Known issues and follow-up

The public hosted workflow can generate Core runtime authority evidence but cannot recreate the private Platform/Cairn environment; release preflight therefore validates the committed canonical Platform evidence. Refreshed `3.29.0` observability evidence remains required before publication and needs explicit authorization for its separate local logging stacks and volumes. The in-cluster restore certification uses a PostgreSQL template snapshot and does not replace an operator-owned portable dump/restore rehearsal where the deployment plan requires one. The compatibility artifact and command names containing `init-parity` remain temporarily to avoid breaking release automation, but they now certify migration authority and duplicate-schema retirement.
