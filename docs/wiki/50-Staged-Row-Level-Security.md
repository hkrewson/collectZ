# Staged Row-Level Security

## Scope and deployment

`3.26.0 — Transaction-Local Workspace Scope and Saved-View RLS Pilot` enables RLS only on `saved_library_views`. Other domains, authentication/bootstrap tables, workers, and provider jobs remain outside the pilot. Application membership, permissions, owner, and library predicates remain required. The maintained saved-view paths are the four CRUD routes in `backend/routes/libraries.js`; no maintained worker or provider accesses this table. Library removal archives rather than hard-deleting libraries.

Migration `124` creates an owner-only `collectz_scope` schema, functions and policies. The migrate job then provisions the normal non-owner runtime login and a separate scope-broker login. Only the broker can execute the grant/revoke functions; it cannot read or mutate application or scope tables directly. The runtime role can evaluate its own grant but cannot create/read/change grants or assume the broker role. All SECURITY DEFINER functions have a fixed `pg_catalog` search path and fully qualified application relations. Private tables and functions revoke PUBLIC privileges. Ownership certification inventories the private authorization tables as well as public tables.

The broker password is a domain-separated HMAC of the high-entropy runtime password; provisioning sends only a SCRAM verifier, never a plaintext password in SQL. No new operator secret is required. Rotation reprovisions both logins; recreate the backend at the same time. The function owner must be able to inspect runtime `pg_stat_activity.backend_xid` (the standard Compose migration owner is a superuser; managed PostgreSQL needs equivalent statistics visibility, such as `pg_read_all_stats`, granted deliberately by its administrator). External-mode startup independently rejects an unavailable or overprivileged broker. The backend retains no schema-owner credential. An application-process compromise that exposes both database credentials is outside this database-role isolation guarantee.

## Transaction contract

`withScopedTransaction(pool, scope, work)` validates positive PostgreSQL integer workspace/library identifiers before acquiring a connection and binds transaction-local settings. Transactions explicitly use READ COMMITTED so the independently committed broker grant is visible even when a connection has a different default isolation level. All database work must use the supplied client; do not issue transaction-control SQL, nest transactions, or perform external provider calls inside the callback. It commits/rolls back before releasing the connection, and discards the connection if rollback fails.

`withSavedViewTransaction` adds the authorization boundary. Callers supply already-authorized request scope and actor. A separate broker connection grants precisely the runtime login, backend PID, full transaction ID, server incarnation, workspace, optional library, and actor. The grant cannot be replayed by a second connection or subsequent transaction. It expires after five minutes and is revoked on completion; stale expired records are pruned during subsequent authorization. Custom PostgreSQL settings are context only: changing them cannot forge a grant or broaden a policy.

Policy USING and WITH CHECK require the matching grant and row ownership. Optional library scope means all libraries in the same workspace for the same owner; a supplied library restricts rows to that library. Non-null row libraries must belong to the same workspace and remain active. An update trigger rejects changes to owner/workspace/library, and a delete trigger also guards foreign-key cascades, which otherwise bypass RLS. Requests send success only after the database commit. Audit logging remains outside the short transaction.

## Upgrade and rollback

Existing views with a library and missing workspace are backfilled from that library. Null or inconsistent ownership that cannot be resolved this way aborts the entire migration; inspect those rows under the owner credential and resolve them deliberately before retrying. No rows are deleted or assigned a guessed owner/workspace. The local canonical database had zero saved views before activation; synthetic legacy rows certify the upgrade path.

Restore the pre-upgrade snapshot and corresponding application images together when rolling back. Old backend images do not bind scope and cannot read views under the new policies. A restored database retains policies/functions; role provisioning must match the selected version. Transient grants are not durable user data: transaction IDs, backend PIDs, server incarnation and expiry prevent reuse by a different session after restore. Never disable policies as an undocumented workaround.

## Verification and evidence

- `test:unit` includes six focused scoped-transaction/broker tests for validation, transaction-local binding, rollback paths and connection disposal.
- `test:scoped-transaction-smoke` uses the existing backend runtime credential and a one-connection pool to prove settings clear on the same PostgreSQL session after commit/rollback. It creates no rows, containers or volumes.
- `test:saved-view-rls-certification` requires `RLS_CERT_ADMIN_URL`. It creates scratch databases and ephemeral runtime/broker roles within the existing PostgreSQL service, migrates legacy rows through 124, and checks CRUD without application predicates, missing scope, forged settings, denied grant-table/function access, broker table denial, parent cascades, actor/library/workspace isolation, WITH CHECK, immutable ownership, concurrency, transaction replay, expiry, ambiguous-ownership rollback and snapshot restore. It cleans up its own databases and roles. `RLS_CERT_OUTPUT` selects the sanitized JSON artifact. A failed label identifies the boundary to investigate; never retain connection URLs, passwords, cookies or SQL grant credentials in evidence.
- `test:saved-view-rls-http-smoke` runs against the canonical backend with its runtime credential and `BASE_URL=http://frontend:3000`. It creates ephemeral users/scopes, verifies all four routes and isolation, and removes its fixture views through authorized transactions before deleting fixture parents.
- `test:init-parity` now compares policy definitions, RLS table flags and private function definitions as well as existing schema fingerprints. Runtime-role and identity/restore certification remain required.
- Hosted migration-check uploads `saved-view-rls-evidence`; release preflight requires its passed checks. Hosted RBAC runs the HTTP smoke. See `docs/wiki/10-CI-CD-and-Registry-Deploy.md` and `docs/wiki/17-Release-Go-No-Go-Checklist.md` for remaining release gates.

Broader table-family activation and job/maintenance scope adoption remain unscheduled backlog work. Local release gates and their exact blockers are recorded in the roadmap closeout; the milestone is not release-ready until those checks are accounted for.
